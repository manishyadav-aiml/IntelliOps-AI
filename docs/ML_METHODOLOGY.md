# ML methodology

## Preprocessing
Parsed entries become a frame of (timestamp, level, service, template). Entries **without a timestamp are excluded** from
detection (and counted in the response) because they cannot be assigned to a window.

## Features (per time window; default 60 s, 300 s supported)
INFO/WARNING/ERROR/CRITICAL counts, error ratio ((ERROR+CRITICAL)/volume), warning ratio, unique and repeated templates, busiest-service
event count and number of services, log volume, **change in error frequency vs the previous window** and mean seconds between errors.
Features of window *t* use only events in *t* and counts of earlier windows; a unit test appends future data and verifies earlier rows are unchanged.

## Detectors
* **Baseline** (`baseline-v1`, no training): per feature, a robust z-score against the *earlier* windows only (median/MAD, expanding history, first 5 windows unscored); threshold 3.5. Scores are z-values.
* **Isolation Forest** (primary ML model): StandardScaler + `IsolationForest`; score = `-score_samples`; threshold = a training-score quantile (default 0.99) unless `ANOMALY_THRESHOLD` overrides it. Contributing features = top absolute z-scores vs the training distribution.
* **Local Outlier Factor** (`novelty=True`): comparison model used in experiments.
* Models are persisted with joblib (`models/anomaly_<version>.joblib` + `latest.json`); `joblib` files are pickles, so only load files from a directory you control.
* `anomaly_score` is **uncalibrated and not a probability**.

**Known limitation (tested):** Isolation Forest cannot rate a window as more anomalous than the most extreme window seen in training. A model trained
only on quiet traffic ranked a 30-error burst below a one-error blip window. Therefore (a) train on data that includes some past incidents, and
(b) `detect_anomalies` also runs the baseline on windows the model did not flag and keeps those detections, labelled `baseline_robust_zscore`.
Both behaviours have regression tests (`test_known_limitation_...`, `test_baseline_safeguard_...`).

## Root-cause evidence (deterministic)
`ml/root_cause.py` compares an incident's window with the 30 minutes before it and reports: which services' errors started earliest, error templates never seen in the baseline, templates whose rate rose >= 3x (min. 5 occurrences), and templates that were frequent before and vanished. It needs no training and no LLM, is stored on the incident (`anomaly_summary.rca`), is fed to the AI assistant as numbered evidence and is printed in reports. It reports **temporal correlation only**: every result carries a disclaimer and nothing is ever labelled a confirmed root cause. With no baseline period in the file it says so instead of inventing 'new' patterns. On the synthetic payment incident it reports that database errors began first, three new error patterns, and that payment-authorisation and login templates stopped appearing.

## Severity
Rule-based and explained (`ml/severity_classifier.py`): P1 for e.g. >=3 CRITICAL events, widespread high error rate, anomaly score >=2x threshold with >=20 errors, or a match with a past P1 pattern; P2/P3/P4 by progressively weaker conditions. A supervised classifier is **not implemented** (LogHub has no severity labels).

## Evaluation
`app/ml/evaluation.py` and `experiments.py` compute precision, recall, F1, PR-AUC, false-positive rate and the confusion matrix on a held-out split.
For HDFS the split is **by block id** (`GroupShuffleSplit`; an assertion checks no block is on both sides); the vocabulary and scaler are fitted on the train split only;
the threshold is a quantile of *train* scores (labels are used only afterwards for metrics).
